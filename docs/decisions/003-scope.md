# 决策 003：使用范围

**状态**：已确定
**日期**：2026-08-02

## 决定

**目前只给自家孩子使用。**

## 不做什么

- 不做注册流程、不做找回密码、不做多租户
- 不做付费、订阅、试用期
- 不做用户运营相关的一切（邀请、排行榜、社区）

这些省下的工作量是巨大的，直接砍掉。

## 但有一件事不能省：访问控制

产品要部署在 `beatfable.com` 这个**公网域名**上。
「只给自家孩子用」不等于「不需要拦人」——公网上任何人都能访问到这个地址。

需要拦的原因不是怕别人来背单词，而是：

1. **上传接口会被滥用** —— 识别要调用多模态模型，按次计费，裸奔等于让别人花你的钱
2. **发音评测同理** —— 每次调用都是成本
3. 数据里有孩子的学习记录

### 方案对比

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| **共享口令**（推荐） | 一个密码，输入后种 Cookie，有效期长 | 最简单，够用，孩子换设备重输一次即可 |
| Cloudflare Access | 平台级拦截，配邮箱白名单 | 更严格，但孩子登录邮箱麻烦 |
| ChatGPT 登录 | 模板自带 `app/chatgpt-auth.ts` 现成的 | 需要孩子有 ChatGPT 账号，不现实 |
| 不拦 | —— | **不可接受**，见上方三条原因 |

**第一步用共享口令。** 实现只需一个中间件校验 Cookie，几十行代码。

## 数据模型仍然带 user_id

虽然当前只有一个使用者，**建表时仍保留 `user_id` 字段**。

理由不是「将来要放开」，而是：

- 第二步上小程序时，微信登录天然带 openid，届时不用改表结构
- 家长端与学生端若要分离（家长审核识别结果、看进度），也需要区分身份
- 成本几乎为零，事后加则要迁移数据

第一步固定填一个常量用户即可。

## 与决策 002 的衔接

「只给自家孩子用」使得发音评测的成本问题彻底消失——
单用户的调用量在任何服务商的计费体系里都接近于零。
因此**决策 002 选服务商时应优先考虑效果，而不是单价**。
