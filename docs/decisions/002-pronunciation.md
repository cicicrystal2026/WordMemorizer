# 决策 002：发音与跟读评测

**状态**：已确定方向，服务商待最终确认
**日期**：2026-08-02

## 决定

- 孩子跟读后需要**能纠正发音**，不只是录音回放
- 发音口音统一为**英式（en-GB）**

## 这是竞品的空白区

五批共 22 张截图里，麦克风出现在三处（拍照阅读当前卡片、单元学习音标旁、
例句卡内），**但始终没有出现分数、评级、发音诊断或错音标注**。
考虑到竞品在发音教学上的投入（可点击音素块、口型示范视频、四个发音人），
若真做了评测不至于一次都不展示。

判断：竞品只做「录音—回放—自我对比」。**做了评测就是差异化能力。**

## 现有代码必须改

`app/page.tsx:67` 当前是：

```ts
utterance.lang = "en-US";
```

**与英式发音要求冲突**，且浏览器内置 TTS 的英音质量不可控（取决于用户系统装了什么语音包）。
需换成云端 TTS 的 en-GB 神经语音，音频缓存到 R2 避免重复调用。

## 两件不同的事，不要混

| 能力 | 作用 | 技术 |
| --- | --- | --- |
| **TTS** | App 读给孩子听 | 文字转语音，en-GB 神经语音 |
| **发音评测** | 判断孩子读得对不对 | 录音 + 音素级打分 |

第二件才是「纠正发音」的核心。评测要能给到**音素级**结果，
否则只能说「你读错了」，说不出「错在哪个音」——那对纠正没有实际帮助。

## 服务商方案

### 推荐：Azure Speech（发音评估 Pronunciation Assessment）

理由：

- **明确支持 en-GB**，与英式发音要求一致
- 返回**音素级得分**，可以精确标出哪个音读错了
- 同时提供准确度 / 流利度 / 完整度 / 韵律 四个维度
- **TTS 与评测同一家**，en-GB 神经语音可直接用，口音与评测标准一致
- 浏览器端有 JS SDK，可实时反馈

### 备选：讯飞等境内厂商

境内延迟低，第二步做小程序时对备案更友好。
但英式发音的支持程度需实测确认，国内英语评测产品多面向教学标准音，
未必严格区分英美。**不作为第一步选型，留作第二步评估。**

### 调用方式

不要把密钥放进前端。两种模式：

| 模式 | 流程 | 取舍 |
| --- | --- | --- |
| **临时令牌**（推荐） | Worker 签发短期 token → 浏览器 SDK 直连 Azure | 延迟低、可实时反馈；密钥不出服务端 |
| 服务端中转 | 浏览器上传音频 → Worker 调 REST → 返回结果 | 完全可控，但多一跳延迟 |

第一步用临时令牌模式，实时性对跟读体验影响很大。

## 成本

单用户场景，量级极小。按每天 100 词、每词约 2 秒计算，
每天音频总时长不到 4 分钟。**这个量级下评测和 TTS 的费用都可以忽略**，
且 TTS 结果缓存到 R2 后，同一个词只需合成一次。

具体单价在接入前需到服务商官网核实，不在此写死。

## 录音数据的处理原则

评测对象是未成年人的语音。虽然是家长为自己孩子使用，仍按最小化处理：

- 录音**用完即弃**，评测返回结果后不长期留存原始音频
- 只保留结构化的评测结果（分数、错音音素），不保留可还原声音的数据
- 若将来要做「跟读回放对比」，音频存本地 IndexedDB，不上传服务端
