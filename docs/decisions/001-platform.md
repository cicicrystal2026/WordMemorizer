# 决策 001：产品形态

**状态**：已确定
**日期**：2026-08-02

## 决定

第一步做 **Web 端**，同时适配桌面与手机浏览器。
第二步上 **微信小程序**。

## 对第一步架构的影响

小程序**无法复用任何 Web 前端代码**——它有自己的 WXML/WXSS/JS 体系，
React 组件、Next.js 路由、RSC 全部用不上。第二步的前端必然重写。

但**后端可以完全复用，前提是第一步就把它写成独立的 HTTP API**。

因此第一步必须遵守一条约束：

> **所有业务逻辑放在 `app/api/*` 的 Route Handler 里，以 JSON 进出。
> 页面只负责调用 API 和渲染，不承载业务逻辑。**

具体地：

| 写法 | 是否可用 | 原因 |
| --- | --- | --- |
| `app/api/words/route.ts` 返回 JSON | ✅ 推荐 | 小程序可直接 `wx.request` 调用 |
| Server Actions（`"use server"`） | ❌ 避免 | 走 RSC 私有协议，小程序调不了 |
| Server Component 里直接查库并渲染 | ❌ 避免 | 逻辑与页面耦合，第二步要重写一遍 |
| 客户端组件 `fetch('/api/...')` | ✅ 推荐 | 与小程序调用同一套接口 |

代价是第一步放弃了 Next.js 的一部分便利（Server Actions 写起来更快），
换来的是第二步只写 UI、不碰后端。**按「第二步一定要做」的前提，这个交换是划算的。**

## 第二步的已知障碍：ICP 备案

微信小程序要求 `request` 的**服务器域名必须完成 ICP 备案**，且配置进
小程序后台的合法域名白名单。开发者工具里可以临时跳过校验，**但正式版强制执行**。

而当前架构是 **Cloudflare Workers**，`beatfable.com` 若未备案，
小程序正式版将无法调用后端。

三条可选路径，第二步再定，但**现在就要知道有这道坎**：

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| A. 境内反向代理 | 在腾讯云/阿里云放一台已备案域名的机器，转发到 Workers | 多一跳延迟，多一份运维 |
| B. 后端迁到腾讯云 | 彻底迁移 | D1 / R2 需换成对应产品，有迁移成本 |
| C. 微信云开发 CloudBase | 小程序调用云函数**无需备案域名**，是常见解法 | 后端逻辑要移植一份 |

无论走哪条，**第一步把 API 写薄、写成标准 HTTP + JSON，迁移成本都最低**。
数据层已用 Drizzle ORM，schema 本身是可移植的（D1 即 SQLite）。

另需注意：小程序**教育类目对个人主体有资质限制**，若以个人身份注册可能受限。
第二步启动前需先确认主体资质，这不是技术问题但会卡进度。

## Web 端的适配要求

「Web 端 + 手机端」指同一套响应式页面，不做两套。
现有 `app/page.tsx` 已是移动优先布局（`app-shell`、`bottom-nav` 等），
桌面端需要补足宽屏适配。

建议同时做成 **PWA**（可添加到主屏幕），成本低，能在小程序上线前
先给孩子一个接近原生的入口。
