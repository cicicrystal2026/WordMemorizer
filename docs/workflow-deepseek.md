# 协同开发：Claude 做技术总监，DeepSeek 做编码执行

## 为什么这么分

两个模型的成本差一个数量级，但**产出质量的差距不是均匀分布的**：

| 环节 | 差距 | 归谁 |
| --- | --- | --- |
| 想清楚要做什么、边界在哪 | 大 | Claude |
| 判断一个取舍的长期代价 | 大 | Claude |
| 按明确规格写出实现 | 小 | DeepSeek |
| 按明确用例修到测试全绿 | 小 | DeepSeek |
| 决定「测试全绿是否等于做完」 | 大 | Claude |

所以分工不是「贵的干难的、便宜的干简单的」，而是
**把判断力留给 Claude，把打字量交给 DeepSeek**。
这条线一旦模糊——比如让 DeepSeek 自己决定要不要改 schema——
省下的钱会以返工的形式加倍还回去。

## 一、接入方式

Claude Code 的模型后端可以换成任何「说 Anthropic Messages 协议」的服务。
DeepSeek 提供了这样一个兼容端点，所以不需要中间代理，三个环境变量就够：

```powershell
$env:ANTHROPIC_BASE_URL        = "https://api.deepseek.com/anthropic"
$env:ANTHROPIC_AUTH_TOKEN      = "sk-你的密钥"
$env:ANTHROPIC_MODEL           = "deepseek-chat"
$env:ANTHROPIC_SMALL_FAST_MODEL = "deepseek-chat"
claude
```

第四个变量容易漏：CLI 会用一个「小快模型」做生成标题、压缩上下文这类后台活。
不设它，这些请求会打向 Anthropic，而你的账号凭据已经被换成 DeepSeek 的，
结果是每隔一会儿弹一次认证错误。

**不要用 `setx` 把这四个变量设成系统级**。设成系统级之后，你哪怕想用回
Anthropic 官方模型也用不了了，而且很容易忘记自己当前连的是谁。
用 `scripts/dev-deepseek.ps1`，它只在当前进程注入，关掉窗口就恢复。

### 首次配置

```powershell
# 1. 密钥存成用户级环境变量（只存密钥，不存端点配置）
setx DEEPSEEK_API_KEY "sk-你的密钥"

# 2. 关掉 PowerShell 窗口重开（setx 对当前窗口不生效）

# 3. 验证连通性，不启动 CLI
cd D:\codex-project\beidancishenqi
.\scripts\dev-deepseek.ps1 -CheckOnly

# 4. 验证通过后正式启动
.\scripts\dev-deepseek.ps1
```

脚本会在启动前打一次真实请求。**模型 ID 是最容易出错的一环**——
`deepseek-chat` 是指向最新通用模型的别名，出新版本时自动跟进，
所以一般不用改；但如果 DeepSeek 改了命名，验证会立刻失败并提示你去控制台核对，
而不是等 CLI 跑到一半吐出一串看不懂的流式错误。

### 换回官方模型

直接新开一个 PowerShell 窗口跑 `claude` 即可。两个窗口可以并存，
一个连 DeepSeek 一个连官方，互不影响。

## 二、换后端后要接受的三个限制

这些不是配置问题，是模型能力差异，只能靠工作方式绕开：

**1. 长上下文里会丢细节。**
所以任务规格要写成自包含的一页纸，不要让它「读完整个仓库自己领会」。
`docs/tasks/*.md` 的每一份都明确列出**必须改动的文件**，就是为这个。

**2. 工具调用没那么稳。**
表现为该改 A 文件却去改了 B、或者声称跑过测试其实没跑。
对策是验收只认 `git diff --stat` 和三道门的真实输出，不认它的自述。

**3. 不做架构判断。**
它会老实按规格实现，包括老实实现一个错误的规格。
规格里的取舍如果我写错了，DeepSeek 不会拦你——这部分风险由我承担。

## 三、协作循环

```
  ┌─ ① 我写任务规格 docs/tasks/NNN-*.md（含测试用例与文件清单）
  │        │
  │        ▼
  │  ② 你本地跑 dev-deepseek.ps1，把规格路径喂给它
  │        │
  │        ▼
  │  ③ DeepSeek 实现 → 三道门全绿 → 提交到分支
  │        │
  │        ▼
  │  ④ 你 git push
  │        │
  │        ▼
  └─ ⑤ 我验收：文件清单对照 + 抽查实现 + 更新 backlog → 回到 ①
```

### 第 ② 步：喂给 DeepSeek 的话

**不要口头描述需求**，指向规格文件。固定用这段：

```
读 AGENTS.md 和 docs/tasks/002-session-logic.md，完整实现这个任务。

要求：
1. 只改规格里「必须改动的文件」列出的那些文件
2. 实现完依次跑 npm run typecheck、npm test、npm run lint
3. 三个都过了再告诉我，并贴出 git diff --stat 的输出
4. 不要修改已有测试来让它通过
5. 遇到规格写得不清楚的地方，停下来问我，不要自己发挥
```

第 5 条最重要。DeepSeek 遇到规格空白时倾向于自己补一个实现，
而那正是最容易出错的地方——它补的往往是**能过测试但语义不对**的版本。

### 第 ⑤ 步：我的验收动作

固定三步，不省：

1. `git diff --stat` 对照规格里的文件清单——**改动文件对不上就是没做完**，
   任务 001 就是函数写对了但没人调用，三道门全绿却等于没做
2. 三道门的真实输出（不看它的自述）
3. 抽查实现：随机挑一个规格里的边界条件，看代码里是否真的处理了

## 四、什么任务不能交给 DeepSeek

以下改动即使写了规格也自己做，因为出错的代价不对称：

| 类型 | 原因 |
| --- | --- |
| `db/schema.ts` 表结构变更 | 迁移一旦生成就难回退，且影响所有下游 |
| `lib/scheduler.ts` 的间隔算法语义 | 改错不会报错，只会让孩子的复习节奏悄悄失效 |
| D1 批量写入的分批逻辑 | 见 AGENTS.md 约束 2，踩过一次 |
| 认证与会话（`lib/auth.ts`） | 安全边界 |
| 任何「顺手重构一下」 | 没有规格就没有验收标准 |
| 配色与可视化取色 | 需要跑校验脚本，见 AGENTS.md 约束 6 |

## 五、成本预期

DeepSeek 的定价请以控制台为准（会调整，这里不抄死数字）。
真正影响账单的不是单价，是**上下文长度**：

- 每个任务开一个新会话，做完就 `/clear`。不要一个会话连做三个任务——
  第三个任务的每一轮都在为前两个任务的历史付费
- 任务规格控制在一页纸内。这既是省钱，也是前面说的「长上下文丢细节」的对策
- 让它贴 `git diff --stat` 而不是完整 diff
